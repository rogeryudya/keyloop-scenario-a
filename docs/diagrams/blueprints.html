What happens to a booking request

A POST /v1/appointments passes six checkpoints. Each one can turn the request away with its own status and code; only a request that passes them all is stored. Steps 2 to 6 run in one database transaction, so a rejection never leaves anything half-written.

Checkpoint Response Error code(s) Example Trace outcome
1 · Validate (before the use case runs) 400 VALIDATION_FAILED with details[] bad UUID, start without an offset, an extra serviceBayId field no handler span
2 · Known Idempotency-Key 201 none: the original booking is replayed a client retries after a timeout success
422 IDEMPOTENCY_KEY_REUSED same key, different booking rejected
3 · References exist 404 DEALERSHIP_ / SERVICE_TYPE_ / CUSTOMER_ / VEHICLE_NOT_FOUND unknown vehicle id not_found
4 · Business rules 422 VEHICLE_NOT_OWNED_BY_CUSTOMER, APPOINTMENT_IN_PAST, OUTSIDE_OPENING_HOURS a 2-hour service at 15:30 when it closes at 17:00 rejected
5 · Allocate 422 SERVICE_TYPE_NOT_SUPPORTED EV battery check at Hanoi rejected
409 NO_SERVICE_BAY_AVAILABLE, then NO_TECHNICIAN_AVAILABLE Hanoi's only bay is taken conflict
6 · Insert lost a race retry, then 409 APPOINTMENT_CONFLICT after 3 retries 10 identical requests at the same moment conflict
Anywhere 500 INTERNAL_ERROR the database is unreachable error (span marked as error)

What runs where, and on which port

docker compose --profile app up --build -d --wait starts everything below on one Docker network. floci plays AWS: it answers AWS API calls on :4566 and starts real containers (Postgres, its console, a registry, ECS tasks) through the Docker socket.

Host port What Open it for
3000 API (NestJS) Swagger /docs, /health, /v1/…
3001 Grafana (in otel-lgtm) traces, logs, metrics under Explore
4317 / 4318 OTLP gRPC / HTTP (otel-lgtm) telemetry in; the API uses 4318
4566 floci: every AWS API, plus the console at /_floci/ui AWS CLI / SDK with --endpoint-url; the browser console
7001 (7001–7099) RDS proxy in floci → Postgres 5432 a database client; credentials in secret keyloop/local/db
8080 ALB listener (only after pnpm infra:ecs) the API running as an ECS service

Startup order

  1. floci becomes healthy (AWS APIs on :4566).
  2. bootstrap runs Terraform: creates the Postgres instance and its secrets.
  3. migrate reads the secret, applies the migrations, loads the seed.
  4. api reads the secret, connects, and turns healthy on /health.

otel-lgtm starts alongside. Each step waits for the one before it to succeed.

Inside the API container

  • NestJS 12 + @nestjs/cqrs: controllers send commands and queries through a bus to one handler per use case.
  • class-validator: request validation at the edge.
  • Prisma 7 + @prisma/adapter-pg, with nestjs-cls transactions around each command.
  • AWS SDK v3 Secrets Manager client: the DB credentials.
  • pino (nestjs-pino) JSON logs and the OpenTelemetry SDK: traces, logs, metrics over OTLP.

Around it

  • Terraform 1.16.5 with the AWS provider: envs/local (data), envs/local-ecs (ECS on floci), envs/aws-dev (real AWS, never applied).
  • Jest + Testcontainers: unit, integration (real Postgres) and end-to-end tests.
  • GitHub Actions: lint, terraform, unit, integration, e2e, smoke, all required on main.
