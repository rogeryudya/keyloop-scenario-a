# 0006 — Data model and double-booking prevention

- **Status:** accepted
- **Date:** 2026-10-12

## Context
The core of the brief is "check availability, then confirm" (FR-1…FR-6). Under concurrent requests (NFR-6), two bookings
can both read "bay 1 and technician A are free from 10:00 to 11:00" and both insert. A check in application code alone
can't prevent that. BR-10 requires that a bay or technician never has two overlapping `CONFIRMED` appointments,
enforced in the database as well as in code.

Shape of the problem:
- Durations vary by service type (30 min to 3 h), so slots aren't fixed cells. Intervals overlap partially, and
  back-to-back appointments must be allowed (BR-2, half-open).
- The bay and technician are chosen by the allocator at booking time (BR-11), so the rows to protect aren't known up front.
- Cancelled appointments must stop blocking straight away (BR-9).

## Decision
**PostgreSQL exclusion constraints are the authoritative guard; the domain check is the fast, explanatory path.**

- `appointments` stores `start_at` / `end_at` (`timestamptz`, UTC). Two constraints, `appointments_no_bay_overlap` and
  `appointments_no_technician_overlap`, use `EXCLUDE USING gist (<resource_id> WITH =, tstzrange(start_at, end_at, '[)') WITH &&) WHERE (status = 'CONFIRMED')`.
  This needs `btree_gist`. `'[)'` gives half-open intervals. The `WHERE` makes cancelled rows not block.
- The handler runs check-and-insert in one READ COMMITTED transaction (A-8). In the common case, the domain
  (`ResourceAllocator`, `TimeSlot.overlaps`) finds a free bay and technician, or returns a specific reason
  (`NO_SERVICE_BAY_AVAILABLE`, `NO_TECHNICIAN_AVAILABLE`).
- When two requests race, the losing insert fails with SQLSTATE `23P01`. The Prisma adapter maps it to
  `AppointmentConflictError`, and the handler retries the whole command (up to 3 times, M2), because another bay or
  technician may still be free. If every attempt fails, the response is 409 `APPOINTMENT_CONFLICT`.
- The other cross-row invariants are also in the schema: composite FKs keep the bay and technician at the same dealership,
  the technician qualified (via `technician_qualifications`), and the vehicle owned by the customer (BR-5). CHECK
  constraints cover `end_at > start_at` and `status` ⇔ `cancelled_at`.

Data model notes:
- Two `timestamptz` columns, not a `tstzrange` column. Prisma has no range type, and the domain `TimeSlot` maps 1:1 to
  two columns. The range is built inside the constraint expression.
- IDs are UUIDs generated by the application, so the domain owns identity and `create()` needs no DB round trip.
- Opening hours are `time` plus an IANA `time_zone`. BR-4 is checked only in the domain (`OpeningHours.contains`),
  because it needs time zone rules the database shouldn't own.
- Prisma can't express the exclusion constraints, CHECK constraints, the partial index or `lower(email)` uniqueness. These
  live in raw SQL in the `m1_constraints` migration, listed in `docs/data-dictionary.md` › Raw SQL constraint names.

## Alternatives considered
- **Application check only:** racy by construction; two transactions both see "free". Rejected.
- **Pessimistic locking (`SELECT … FOR UPDATE` on bay/technician rows):** works, but the handler must lock every
  *candidate* bay and technician before choosing (they aren't known up front), or lock the dealership row, which
  serializes all bookings at a dealership. Lock ordering also has to be managed to avoid deadlocks. Only code that takes
  the lock is protected; a bad SQL script or a future endpoint isn't.
- **Advisory lock per dealership (`pg_advisory_xact_lock`):** simple, but the same drawbacks: it serializes a dealership
  and only protects code paths that remember to take it.
- **SERIALIZABLE isolation:** correct, but it is only guaranteed if every writer uses it. Its predicate locks raise
  serialization failures on reads that merely touch the same index pages, so unrelated bookings get retried too. The
  failure doesn't say which resource clashed.
- **Unique constraint on `(resource_id, slot_start)` over a fixed grid:** only works if every appointment is one grid
  cell. With variable durations it misses partial overlaps unless each appointment writes one row per 15-min cell,
  which adds write amplification and a second representation of the same fact.

## Consequences
- Easier: the database rejects double-booking from any writer (API, seed, manual SQL). Concurrency correctness doesn't
  depend on every code path remembering a lock. Bookings for different bays and technicians proceed in parallel with no
  contention. The GiST indexes behind the constraints also serve "is this resource busy?" queries.
- Harder: Postgres-specific (`btree_gist`, `EXCLUDE`); the Prisma schema isn't the whole truth about the database; raw
  SQL migrations must be kept in sync with `docs/data-dictionary.md`.
- Must remember: the handler needs the 23P01 → `AppointmentConflictError` mapping and a bounded retry (M2). Integration
  tests (M1) must prove the constraint rejects overlaps and accepts back-to-back and cancelled overlaps, and a
  concurrency test (M2) must prove only one of N parallel bookings for the last free slot wins.
